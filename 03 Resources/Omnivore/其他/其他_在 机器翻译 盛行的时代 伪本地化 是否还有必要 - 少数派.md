data-omnivore-anchor-idx="26">虽然不是本地化的专业人员，但我依然想刨根问底，了解伪本地化的目的。当时在我看来本地化与翻译差不太多，只是将源语言替换为目标语言而已。既然如此，为什么还需要一个看似「多此一举」的伪本地化，将文本变成了一个看起来不像英文实则是英文的东西，目的何在？带着这样的疑问，我上网去寻求有关伪本地化的更多信息。</p><p data-omnivore-anchor-idx="27">维基百科是这么解释伪本地化的：</p><blockquote data-omnivore-anchor-idx="28"><p data-omnivore-anchor-idx="29"><strong data-omnivore-anchor-idx="30">伪本地化</strong>是软件测试中用来测试软件是否符合国际化与本地化的方法之一。与正式本地化中将软件文本翻译成外语不同，伪本地化只是改变原始文本的呈现方式而不改变文本本身。这些特定的改变使得原始文字看起来仍可按源语言阅读，但却包含了不同语言间最可能存在的差异：文本或字符的长度变化、语言方向、界面适应等等。</p></blockquote><p data-omnivore-anchor-idx="31">原来，不同语言间的显示差异使得本地化并不是单纯的翻译那么简单，因此，在正式本地化之前，需要测试软件是否具备「可本地化」的能力。下面列举了在本地化中的出现的常见问题。</p><h2 data-omnivore-anchor-idx="32" id="ss-hId-2" hid="ss-hId-2">本地化中的常见问题</h2><h3 data-omnivore-anchor-idx="33">一、字符不同</h3><p data-omnivore-anchor-idx="34">字符不同是不同语言间最直观的差别。比如都使用拉丁字母，相比英语，许多欧洲语言都会有变音符号（diacritical mark），而除了拉丁字母以外，又有西里尔字母、阿拉伯字母等等其它字母系统；相对于字母，中日韩（CJK）字符又另成一类。</p><p data-omnivore-anchor-idx="35">如果编写软件时采用了覆盖范围有限的字符集（比如 ASCII），在本地化时很可能会导致其它语言需要用到的字符无法正常显示。（如下图）</p><figure data-omnivore-anchor-idx="36"><img data-omnivore-anchor-idx="37" LTR）或从右往左（Right-to-Left, RTL），下图展示了两种语言（以英语/阿拉伯语为例）在界面上的差别。注意在软件中，RTL 语言不仅文本需要右对齐，其它控件也需要以从右向左的形式排列（但播放按钮、进度条等元素无需反向）。</p><p data-omnivore-anchor-idx="60">另一个需要考虑的是「双向文本（Bidirectional code，即将数据直接嵌入到程序中，而非从外部获取数据或在运行时生成数据）</strong></h3><p data-omnivore-anchor-idx="66">上面说的是不同语言本身存在的差异，而这里则是在代码层面可能出现的问题。</p><p data-omnivore-anchor-idx="67">字符串分割，表现为一个字符串被拆分成两个或多个部分。这可能会增加翻译的难度，因为翻译人员必须独立地翻译每个部分，而不知道这些部分是相关的。而且，不同的语言可能会要求以不同的顺序组织各个部分或采用完全不同的句子结构。这可能会导致翻译出的句子结构混乱。，</p><p data-omnivore-anchor-idx="68">在 Windows 中，由字符串分割引起的最为知名的翻译问题应该就是「<a data-omnivore-anchor-idx="69" href="https://sspai.com/link?target=https%3A%2F%2Fwww.zhihu.com%2Fquestion%2F31689608%2Fanswer%2F2584011541" target="_blank">该内存不能为 read/written</a>」（正确翻译应为「该内存不能被读取/写入」）了，该语段的英文原文是：<strong data-omnivore-anchor-idx="70">The memory could not be %s. </strong>（其中 %s 表示占位符，将视情况被替换为 read 或 written），由于 read/written 同样未被翻译</figcaption></figure><p data-omnivore-anchor-idx="77">至于硬编码，其弊端已被许多人指出，这里不做详述。从本地化的角度来说，一旦一些字符串被直接写进了源代码中，而并非可用于本地化的资源文件中，在本地化过程中这种字符串可能不会被翻译，从而导致本地化的不完全。其实上面的「该内存不能为 data-omnivore-anchor-idx="142"><p data-omnivore-anchor-idx="143">传统上，软件本地化独立于软件开发过程。在典型情况下，软件将以一种基本语言（例如英语）构建和测试，并将任何<i data-omnivore-anchor-idx="144">可本地化的</i>元素提取到外部资源中。这些资源被交给本地化团队，以翻译成不同的目标语言。这种方法的问题在于，许多细微的软件错误可能会在本地化过程中发现，但那时修复它们为时已晚（或更可能是成本太高）。</p><p data-omnivore-anchor-idx="145">针对一些已然成熟且多数的目标语言翻译已经可以获取的软件而言，或是仅会有少量界面变更的软件，直接将翻译套用至该软件并进行多个语言的测试，可能是最直接且最好的测试方式。而针对一些新开发的软件，或是将会有庞大的界面变更的软件，等待翻译完毕之后再进行界面测试，则可能因此延迟了整个测试的进程。并且，在软件开发的初期也不见得会开始进行界面文字的翻译，因为界面有很大的几率会被调整甚至重新设计。若要等到产品比较成熟后，开始进行界面翻译，然后才进行翻译的界面测试，产品的上市时程将可能因此被延误。在这样的状况之下，伪本地化将会是最佳的选择，原因之一是无需进行真正的翻译。</p></blockquote><p data-omnivore-anchor-idx="146">也就是说，很多时候软件开发与本地化是分离的，如果本地化团队在本地化过程中发现了显示存在问题，就得联系开发团队修改代码，开发团队修改代码再返回本地化团队，这样一来一回很容易影响开发效率。（见下图）</p><figure data-omnivore-anchor-idx="147"><img data-omnivore-anchor-idx="148" data-omnivore-original-src="https://cdnfile.sspai.com/2024/07/09/article/3c473c05eca739771dc7df3478eb6271.jpeg?imageView2/2/format/webp" src="https://proxy-prod.omnivore-image-cache.app/0x0,stxGMgwPa3duJG1130CXu_W2clPjPrRhx-wqHezdWmao/https://cdnfile.sspai.com/2024/07/09/article/3c473c05eca739771dc7df3478eb6271.jpeg?imageView2/2/format/webp" alt="伪翻译" data-original="https://cdnfile.sspai.com/2024/07/09/article/3c473c05eca739771dc7df3478eb6271.jpeg?imageView2/2/format/webp" data-index="15"><figcaption data-omnivore-anchor-idx="149">传统流程与伪本地化流程对比</figcaption></figure><p data-omnivore-anchor-idx="150">而且，如果需要本地化成多种目标语言，而每种语言都存在相同的问题，那么问题数量将成倍增加，修复难度也将直线上升，这会是一件非常可怕的事情。</p><p data-omnivore-anchor-idx="151">而通过伪本地化，开发团队就可以在正式的本地化开始之前就找出潜在的本地化问题，有效减少了本地化过程中出现问题的概率。</p><p data-omnivore-anchor-idx="152">同时，伪本地化可以帮助开发人员无需实际进行真正的翻译，就可了解产品在翻译后的界面外观。</p><blockquote data-omnivore-anchor-idx="153"><p data-omnivore-anchor-idx="154">你可以把伪本地化看作是定期去看牙医。这样你就能尽早发现潜在的蛀牙，避免严重的治疗。</p><p data-omnivore-anchor-idx="155">但是，如果你等到牙痛发作时才去治疗，你将不得不忍受巨大的痛苦。除了浪费时间和金钱进行更复杂的治疗外，你还需要……</p></blockquote><p data-omnivore-anchor-idx="156">开发人员在开发或调试产品时，甚至可以直接将伪本地化作为默认语言环境，这有助于他们将本地化视为优先事项而不是事后考虑，并让他们有机会在设计阶段，或在本地化开始之前解决问题。</p><p data-omnivore-anchor-idx="157">正如微软前软件开发人员 Michael S. Kaplan 所说，</p><blockquote data-omnivore-anchor-idx="158"><p data-omnivore-anchor-idx="159">实际上，我们用伪本地化构建了很多 Windows，并将它们「本地化」为英语！<br data-omnivore-anchor-idx="160">伪本地化就像一个热心、勤奋但天真的实习本地化人员，他（她）将「翻译」每一个字符串，并且可以找到我们从来没有希望在每种语言中都有相同覆盖率的问题——而且比我们以前任何时候都要快。</p></blockquote><h2 data-omnivore-anchor-idx="161" id="ss-hId-5" id="ss-hId-6" hid="ss-hId-6">机器翻译与伪本地化</h2><p data-omnivore-anchor-idx="203">在中文维基百科的「伪本地化」词条上有这样一段话：</p><blockquote data-omnivore-anchor-idx="204"><p data-omnivore-anchor-idx="205">近年来，随着机器翻译技术的进步，借由机器翻译也可达到与伪本地化相当的效果。</p></blockquote><p data-omnivore-anchor-idx="206">早些时候使用伪本地化确实是考虑到开发人员可能不了解其它语言，而现在随着机器翻译的成熟，开发人员也可以直接选择机翻原文来查看本地化效果。那么，如今「伪本地化」是否还有必要呢？</p><p data-omnivore-anchor-idx="207">在我看来还是有必要的，原因如下：</p><ol data-omnivore-anchor-idx="208"><li data-omnivore-anchor-idx="209">伪本地化可以同时对多种语言特征进行模拟，比如既可以测试不同的字符集，也可以模拟文本扩展的情况。这对于需要本地化为多种语言的软件来说还是必要的。</li><li data-omnivore-anchor-idx="210">伪本地化不对源语言本身进行调整，只是改变了它的呈现方式。这样开发人员在伪本地化环境下仍然可以阅读文本。而如果使用机翻的话，如果开发人员不了解翻译后的语言，就仍需回到原始语言开发软件。因此，伪本地化可帮助开发人员发现本地化问题，仍可保证原文（对于开发人员）的可读性。</li></ol><p data-omnivore-anchor-idx="211">这也是直到现在，伪本地化仍然是测试本地化的一种重要方式，被许多公司所采用，经久不衰的其中一些原因。</p><hr data-omnivore-anchor-idx="212"><h2 data-omnivore-anchor-idx="213" id="ss-hId-7" hid="ss-hId-7">参考资料</h2><ol
