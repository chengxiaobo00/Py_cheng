# 除了显卡，玩转大模型的门槛还在哪？ - 少数派

<DIV id="readability-content"><DIV data-omnivore-anchor-idx="1" class="page" id="readability-page-1"><div data-omnivore-anchor-idx="2" data-v-39bff104="" data-v-4c610104=""><div data-omnivore-anchor-idx="3" data-v-4c610104=""><p data-omnivore-anchor-idx="4">大语言模型（Large Language Model, LLM,&nbsp;下称大模型）可谓是当下最火的科技。纵使它这么火爆，能够入局的玩家却不多。究其原因，还是玩转大模型的门槛太高了。「拥有」一个专属大模型并不难。参照论文、开源代码、数据集，改一改，总能搓出来一个大模型。但是想要<strong data-omnivore-anchor-idx="5">玩转</strong>，就难了。</p><p data-omnivore-anchor-idx="6">怎样才算玩转？当然是玩着，还把钱挣了。本文尝试从学术界和工业界的双重视角来解释：为了玩转大模型，需要克服哪些门槛？</p><h2 data-omnivore-anchor-idx="7" id="ss-hId-1" hid="ss-hId-1">如何将一个大模型运行起来？</h2><blockquote data-omnivore-anchor-idx="8"><p data-omnivore-anchor-idx="9">GPUs, lots of GPUs.</p></blockquote><p data-omnivore-anchor-idx="10">现在，所有人都知道，跑大语言模型的关键在于显卡（GPU）。谁拥有最多的显卡，谁就有机会发展出更大的模型，提供更好的服务。但是只要有显卡就够了吗？</p><p data-omnivore-anchor-idx="11">答案是：不够。</p><p data-omnivore-anchor-idx="12">目前流行的大语言模型，通常是 Transformer 架构模型，是一类深度神经网络模型。这类模型需要经历训练和推理两个阶段。就像人脑一样，先学习知识，再运用到新的问题上，所谓举一反三。对于企业来说，就需要先拥有一个训练好的模型，再将用户的问题输入到模型中，进行推理，并返回结果。</p><p data-omnivore-anchor-idx="13">理想情况下，如果一块 GPU 训练一个模型要一天，那么两块 GPU 训练相同的模型就只用半天。现实会给你狠狠的一巴掌——钞能力在这不管用。正如《人月神话》讨论工作效率随人数增加，非线性增加的问题，<strong data-omnivore-anchor-idx="14">随着 GPU 数量的增加，模型训练的效率也不是成比例增加的</strong>。业界通常使用加速比（多卡训练下的单卡吞吐量平均指标除以单卡训练下的吞吐量平均指标）来衡量多卡训练的效率，越接近 1 越好。</p><p data-omnivore-anchor-idx="15">以双卡加速比 0.8 为例。这代表着，如果一张卡单独训练时的吞吐率为每秒钟 600 条序列（即每秒钟，显卡可以接收 600 条序列的文字并更新模型参数），那么两张卡时，每张卡每秒钟只能处理 600*0.8 = 480 条序列了，两张卡也才处理 960 条序列。相比较理想情况下，双卡 600*2=1200 条序列，是不是感觉两张卡带来的效率提升也没那么大了？</p><p data-omnivore-anchor-idx="16">GPU 越多，GPU 的吞吐率越小，GPU 吞吐率越小，GPU 越少。所以，GPU 越多，GPU 越少。</p><h2 data-omnivore-anchor-idx="17" id="ss-hId-2" hid="ss-hId-2">一个「GPU 大厂」是如何运转的？</h2><p data-omnivore-anchor-idx="18">假设 GPU 已经不是门槛，厂商就会把这些 GPU 全部放在一起，搭建一个专门的 AI 集群处理 LLM 相关服务流量，称为「<strong data-omnivore-anchor-idx="19">GPU 大厂</strong>」。大厂员工往往干活的时间不多，<strong data-omnivore-anchor-idx="20">更多的时间花费在拉通对齐</strong>，GPU 大厂也不例外。</p><p data-omnivore-anchor-idx="21">GPU 拉通对齐什么呢？</p><p data-omnivore-anchor-idx="22">回答上面的问题，首先要解释一下多卡训练时，每个 GPU 在干嘛。模型训练阶段主要涉及两个部分：数据集和模型参数。随着数据集和模型参数的增加，多卡训练也可以分为数据并行和模型并行。数据并行就是将一整个数据集分成几个小数据集，每个 GPU 负责训练一个小数据集。模型并行就是将模型划分为好几个子模型（按照划分的方式不同，分为张量并行和流水线并行），每个 GPU 负责训练一个子模型。由于训练的过程需要迭代好多轮，所以每一轮结束这些 GPU 都需要进行同步，向别的 GPU 汇报这一轮的工作结果（训练结果）。</p><ul data-omnivore-anchor-idx="23"><li data-omnivore-anchor-idx="24"><strong data-omnivore-anchor-idx="25">流水线并行</strong>：一个 LLM 模型通常包含很多层，每一层需要依次接收上一层的结果作为输入，并将计算结果输出到下一层，涉及到 Send/Recv 通信操作。这类操作通信量不多，是 GPU 所负责的模型层的计算结果，但是由于依赖关系，每一层需要等待上一层的计算结果才可以继续训练，引入了很多等待时间，学术界称为 Bubble 。</li><li data-omnivore-anchor-idx="26"><strong data-omnivore-anchor-idx="27">张量并行</strong>：LLM 模型的一层也可以由几个 GPU 负责训练。这时候拉通对齐的成本就大大增加了。因为单层模型训练涉及到的是矩阵乘法，这里每个元素的计算结果都有赖于周围的元素，所以这里的通信关系就由链式的变成了网状的，一般称为 All-to-All 通信，即每个 GPU 都要和其他 GPU 都通信一次，且每次通信的内容都有所不同。张量并行的通信量是多卡训练中最多的环节，也是最容易产生瓶颈的地方。如果流水线并行看作部门间和部门间的交流，那么张量并行就是部门内部小组成员高强度频繁的交流。</li><li data-omnivore-anchor-idx="28"><strong data-omnivore-anchor-idx="29">数据并行</strong>：当数据集很庞大的时候，可以用多个 GPU 同时训练一个模型，每个模型使用一部分子数据集作为输入，最终每一轮的训练成果汇总到其中一个 GPU，或者同步到全部 GPU 上，通过这种方式能够降低数据集的训练时间。不可避免的需要在训练一段时间后同步一下进度 （Allreduce 操作），否则每个 GPU 上的模型只包含自己训练的数据信息。数据并行的频率和通信量介于流水线并行和张量并行之间。</li></ul><figure data-omnivore-anchor-idx="30"><img data-omnivore-anchor-idx="31" data-omnivore-anchor-idx="37">上述三种并行方式发展的很成熟，并被应用于现在流行的训练框架中（<a data-omnivore-anchor-idx="38" href="https://sspai.com/link?target=https%3A%2F%2Fgithub.com%2Fmicrosoft%2FDeepSpeed" target="_blank">DeepSpeed</a>，<a data-omnivore-anchor-idx="39" href="https://sspai.com/link?target=https%3A%2F%2Fgithub.com%2FNVIDIA%2FMegatron-LM" target="_blank">Megatron-LM</a>）。除了以上最典型的三种并行方式，随着对大模型训练的研究更加深入，一些训练框架应用了如序列并行（<a data-omnivore-anchor-idx="40" href="https://sspai.com/link?target=https%3A%2F%2Fcolossalai.org%2F" target="_blank">Colossal-AI</a>）以及专家并行（<a data-omnivore-anchor-idx="41" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fpdf%2F2201.05596" target="_blank">DeepSpeed-MoE</a>）等手段。这些手段通常针对特定场景或模型，因此不再赘述。</p></blockquote><p data-omnivore-anchor-idx="42">现在的 GPU 性能越来越强，单卡训练的速度越来越快，但是想让这些 GPU 一起高效的干活越来越困难了。研究结果表明<sup data-omnivore-anchor-idx="43" href="" footnote-id="1" data-title="Sapio A, Canini M, Ho C Y, et al. Scaling distributed machine learning with {In-Network} aggregation[C]//18th USENIX Symposium on Networked Systems Design and Implementation (NSDI 21). 2021: 785-808.">1<div data-omnivore-anchor-idx="44"><p data-omnivore-anchor-idx="45">Sapio A, Canini M, Ho C Y, et al. Scaling distributed machine learning with {In-Network} aggregation[C]//18th USENIX Symposium on Networked Systems Design and Implementation (NSDI 21). 2021: 785-808.</p></div></sup>，AI 集群的瓶颈往往在 GPU 间的通信上。在学术界，有一个专门的指标来衡量 GPU 的利用率：MFU。字节跳动最新的研究成果<sup data-omnivore-anchor-idx="46" href="" footnote-id="2" data-title="Jiang Z, Lin H, Zhong Y, et al. {MegaScale}: Scaling Large Language Model Training to More Than 10,000 {GPUs}[C]//21st USENIX Symposium on Networked Systems Design and Implementation (NSDI 24). 2024: 745-760.">2<div data-omnivore-anchor-idx="47"><p data-omnivore-anchor-idx="48">Jiang Z, Lin H, Zhong Y, et al. {MegaScale}: Scaling Large Language Model Training to More Than 10,000 {GPUs}[C]//21st USENIX Symposium on Networked Systems Design and Implementation (NSDI 24). 2024: 745-760.</p></div></sup>，在多达一万显卡的集群进行优化，将 MFU 提高至55%，也就是说 AI 集群有大约一半的时间，GPU 都在「摸鱼」。</p><h2 data-omnivore-anchor-idx="49" id="ss-hId-3" hid="ss-hId-3">GPU 也要降本增效</h2><p data-omnivore-anchor-idx="50">不是 GPU 想摸鱼，是工作内容不得不摸鱼。为了不让 GPU 摸鱼，学界和业界可谓是挖空心思降本增效，试图用更少的 GPU 干更多的活：</p><ul data-omnivore-anchor-idx="51"><li data-omnivore-anchor-idx="52"><strong data-omnivore-anchor-idx="53">流水线编排优化</strong>：GPU 也要做好任务管理。如果每个 GPU 在流水线中都傻傻地等待其他 GPU 完成任务再开始自己的工作，不就可以「摸鱼」了吗，那怎么行！一些工作（<a data-omnivore-anchor-idx="54" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fpdf%2F1811.06965" target="_blank">GPipe</a>，<a data-omnivore-anchor-idx="55" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fpdf%2F1806.03377" target="_blank">PipeDream</a>）通过发掘不同 GPU 间可以独立完成的工作，尽可能小的减少 GPU 间的工作依赖，让每个 GPU 忙完手里的活就赶紧发给下一个 GPU，而不是等所有工作全部忙完再汇报，大大降低 GPU 的摸鱼时间。</li><li data-omnivore-anchor-idx="56"><strong data-omnivore-anchor-idx="57">梯度压缩技术</strong>：一个合格的打工人，不会不加处理地将工作结果汇报给他人，而是整理出有价值的信息汇报，GPU 也不例外。GPU 的每一轮训练结果不一定全部有用，有很多零值，别的 GPU 不关心。因此，一些工作（<a data-omnivore-anchor-idx="58" href="https://sspai.com/link?target=https%3A%2F%2Fsands.kaust.edu.sa%2Fpapers%2Fomnireduce.sigcomm21.pdf" target="_blank">OmniReduce</a>）通过各种手段，例如让 GPU 只发送必要的信息，降低 GPU 发送的数据量，避免时间浪费在收发数据上。</li><li data-omnivore-anchor-idx="59"><strong data-omnivore-anchor-idx="60">网络辅助计算</strong>：大厂员工通常会配备实习生干一些杂活，现在可以招募可编程交换机作为 GPU 的实习生了。不同于传统网络设备只负责转发数据，可编程交换机可以从事简单的计算操作。一些工作（<a data-omnivore-anchor-idx="61" href="https://sspai.com/link?target=https%3A%2F%2Fwww.usenix.org%2Fsystem%2Ffiles%2Fnsdi21-lao.pdf" target="_blank">ATP</a>，<a data-omnivore-anchor-idx="62" href="https://sspai.com/link?target=https%3A%2F%2Fsands.kaust.edu.sa%2Fpapers%2Fswitchml.nsdi21.pdf" target="_blank">SwitchML</a>）基于此特点，在转发 GPU 的数据时提前使用可编程交换机进行计算，从而让 GPU 轻松一点。</li></ul><p data-omnivore-anchor-idx="63">除了直接解决 GPU 使用效率不高的问题，业界还会思考一些其他更现实的问题：</p><ul data-omnivore-anchor-idx="64"><li data-omnivore-anchor-idx="65"><strong data-omnivore-anchor-idx="66">异构 GPU 集群增效</strong>：鸡蛋不能放在一个篮子里，公司采购的 GPU 也不能是一个厂商的（现在最流行的如 NVIDIA 和华为昇腾）。不同厂商的 GPU 性能指标会有所不同，一些工作提出管理和调度接口，用于统一管理和分配异构 GPU 资源，保证不同型号 GPU 的性能差异不会影响集群整体性能。</li><li data-omnivore-anchor-idx="67"><strong data-omnivore-anchor-idx="68">提高 GPU 集群弹性</strong>：人会生病，GPU 也会。在真实场景下，在 1000 个 GPU 上同时运行程序，很大概率会出现一些 GPU 无法使用。为了让训练进度不被失效的 GPU 拖慢，一些工作（<a data-omnivore-anchor-idx="69" href="https://sspai.com/link?target=https%3A%2F%2Fwww.cs.rice.edu%2F~eugeneng%2Fpapers%2FSOSP23.pdf" target="_blank">Gemini</a>，<a data-omnivore-anchor-idx="70" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fpdf%2F2002.05814" target="_blank">Hoplite</a>）考虑快速地恢复失效 GPU 负责的程序或者重新规划现有 GPU 的训练内容。</li><li data-omnivore-anchor-idx="71"><strong data-omnivore-anchor-idx="72">提高 GPU 碎片利用率</strong>：现在的 GPU 单个算力性能往往过剩，如果一个 GPU 只负责一个任务，算力很难被压榨干净。为了赚更多钱，集群中的 GPU 会同时负责多个模型训练任务 。好钢要用在刀刃上。一些工作（<a data-omnivore-anchor-idx="73" href="https://sspai.com/link?target=https%3A%2F%2Fcse.hkust.edu.hk%2F~weiwa%2Fpapers%2Ffgd-atc23.pdf" target="_blank">FGD</a>，<a data-omnivore-anchor-idx="74" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fpdf%2F2401.08156" target="_blank">GMLake</a>）考虑如何将这些碎片 GPU 资源分配至不同的训练任务，从而刚好满足每个训练任务的需求，不过度分配资源。</li></ul><h2 data-omnivore-anchor-idx="75" id="ss-hId-4" hid="ss-hId-4">从训练到推理</h2><p data-omnivore-anchor-idx="76">模型训练和推理的关系就像是人类学习和学以致用的关系。我们花了大量时间学习，最终是为了将学习的知识应用到实际。</p><p data-omnivore-anchor-idx="77">学习的时候，关注点在学习内容。学以致用时，关注点在反应时间。面对询问，一个人能够很快地做出反应并给出正确答案，我们会夸这个人聪明。大模型也不例外。这就导致模型训练和推理时，业界的关注目标不一样。作为用户，在各个平台和大模型对话，背后都是一个个推理请求，对应了大模型的推理任务。<strong data-omnivore-anchor-idx="78">对于推理任务，无论是用户还是业界，都希望大模型反应速度越快越好，对应的指标就是「推理时延」</strong>。</p><p data-omnivore-anchor-idx="79">从技术的角度，推理任务和训练任务也有所不同，直接给出结论就是：<strong data-omnivore-anchor-idx="80">推理任务对内存访问速度的要求更高</strong>。所以学界和业界开始意识到，针对推理任务，需要从新的角度进行优化。这些优化近期被提出来，思路简单，却能够取得很好的效果：</p><ul data-omnivore-anchor-idx="81"><li data-omnivore-anchor-idx="82"><strong data-omnivore-anchor-idx="83">解耦处理模型推理中的关键阶段</strong>：大模型推理包含两个阶段（Prefill 和 Decoding 阶段），如果不区分这两个阶段，会造成任务的性能干扰。一些工作（<a data-omnivore-anchor-idx="84" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fabs%2F2403.02310" target="_blank">Sarathi</a>，<a data-omnivore-anchor-idx="85" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fabs%2F2401.09670" target="_blank">DistServe</a>）在调度推理任务时将这两个阶段分开考虑，交错不同阶段的请求或分配不同的 GPU 避免干扰，均能达到好几倍的加速效果</li><li data-omnivore-anchor-idx="86"><strong data-omnivore-anchor-idx="87">利用局部性原理优化大模型推理系统</strong>：局部性原理可以看成计算机的就近原则。通过将「局部性原理」应用到大模型推理系统中的模型重载、模型迁移、资源分配，<a data-omnivore-anchor-idx="88" href="https://sspai.com/link?target=https%3A%2F%2Farxiv.org%2Fabs%2F2401.14351" target="_blank">ServerlessLLM（OSDI 24）</a>实现了10～200 倍的推理速度提升</li><li data-omnivore-anchor-idx="89"><strong data-omnivore-anchor-idx="90">使用小模型去代替大模型</strong>：大模型在通用任务上的效果卓越，但是在特定场景下的性能能胜过专用小模型吗？<a data-omnivore-anchor-idx="91" href="https://sspai.com/link?target=https%3A%2F%2Fyidingwang.xyz%2Fpublic%2Ffiles%2Ftabi_eurosys23.pdf" target="_blank">Tabi （Eurosys 23）</a>企图分析用户的请求和小模型的性能，优先使用合适的小模型服务用户请求，在必要时才使用大模型。通过这种方式降低平均推理时延
